Project brief · revision 2

An interactive dashboard of a scale-to-zero AI platform

A living, art-directed miniature of the My Sleepless Slaves AWS deployment. It sleeps when the platform sleeps, wakes when real jobs arrive, replays past runs for visitors, and shows what the platform costs. It doubles as a monitoring view and a portfolio centrepiece.

Owner: platform authorRegion: eu-north-1Revised 2026-11-17 against the platform repo

00What changed in this revision

The first draft was strong on ambition and art direction. It was checked line by line against the platform repo (Terraform, Kubernetes manifests, service code, architecture docs). These are the corrections and gaps that change the design.

Security finding, outside this project

The wake API's $default route has no authorizer, and the Lambda answers POST /wake and POST /jobs with Access-Control-Allow-Origin: *. Anyone with the URL can start the control plane and enqueue work. The public dashboard must never reveal or call this URL. Fixing it belongs in the platform repo and is the owner's call.

Naming, owner's decision

The public site will be seen by recruiters. Decide whether it carries the platform's internal name or a public-facing one. The architecture docs already use "Personal AI Platform".

01Goal, audience and success

Build an interactive 2.5D/3D environment where each AWS resource and service is a recognisable object, and real platform events drive what moves, lights up and powers down. The dashboard explains the architecture through space, motion and story rather than through boxes and charts.

Who it is for

  • Recruiters and non-engineers: understand in 60 seconds that this system sleeps to save money and wakes on demand.
  • Engineers: inspect any component, see real timings, failure paths and costs.
  • The owner: glance at live state and spend.

Done looks like

  • A visitor can replay a real run end to end with a timeline and captions.
  • Live mode reflects the real state within about 15 seconds of an AWS event.
  • Every animated state is labelled observed or inferred.
  • Works on a mid-range phone; has a non-WebGL fallback.
  • Hosting costs under $5/month at rest.

Non-goals

  • No controls: the public dashboard never starts, stops, scales or submits anything.
  • No job contents, prompts, CVs or model outputs are shown anywhere.
  • Not a replacement for CloudWatch; deep debugging stays there.
  • No hand-modelled Blender scene in the first version.

03The real lifecycle of a job

The draft listed 16 steps in one line. Real runs branch, overlap and fail. The dashboard's state machine follows this graph, and each edge is an event the dashboard can observe or infer.

flowchart TD
  A[Request at API Gateway] --> B[Lambda]
  P[06:55 pre-warm cron] --> B
  B -->|SendMessage| Q1[(Workflow queue)]
  B -->|StartInstances if stopped| CP[Control plane boots]
  D[Direct POST via SSM tunnel] --> Q1
  CP --> K[K3s pods ready]
  K --> W[Worker takes job from workflow queue]
  Q1 --> W
  W --> L1{LAYA}
  L1 -->|decision-only job| R1[Result to S3: completed on CPU]
  L1 -->|below relevance threshold| R2[Result to S3: rejected, GPU never wakes]
  L1 -->|passes| Q2[(GPU queue)]
  Q2 --> KE[KEDA scales vLLM 0 to 1]
  KE --> PE[vLLM pod pending]
  PE --> CA[Cluster Autoscaler sets ASG desired 1]
  CA --> G[GPU instance launches in 1c]
  G --> EB[Model EBS attached and mounted]
  EB --> J[Node joins K3s]
  J --> V[vLLM loads qwen-general, becomes ready]
  V --> GEN[Worker calls LiteLLM to vLLM]
  GEN --> L2{LAYA verifies}
  L2 -->|fails, retries left| GEN
  L2 -->|passes| R3[Result to S3: completed]
  L2 -->|fails, no retries left| R4[Result to S3: needs_review]
  GEN -.->|error or Spot reclaim| RT[Message reappears, retried]
  RT -.->|3rd failure| DLQ[(DLQ)]
  R3 --> CD[KEDA cooldown 120 s, vLLM to 0]
  CD --> SD[CA removes node after 2 min, ASG to 0]
  SD --> IW[Watchdog: 30 min quiet]
  IW --> ST[Control plane stops]
  ST --> GU[EventBridge guard: ASG 0, launches suspended]

Cases the dashboard must handle

  • Parallel work: several jobs in either queue at once; one GPU serving them in sequence.
  • Warm path: a job arrives while the GPU is still up inside its cooldown, so no cold start.
  • Wake with no work: the pre-warm cron, or a /wake call, boots the control plane and it idles back to sleep.
  • Synchronous calls to LiteLLM that skip both queues. KEDA does not see them.
  • Launch failure: the ASG can't get capacity (or Spot is denied) and the GPU job waits.
  • Spot interruption warning once Spot is enabled.
  • Crash recovery: worker restarts and replays pending outbox events.

04Art direction to start from

The draft asked for original metaphors. The owner has already produced 23 isometric component renders in Assets/3d components/ (an idle and a working set). They set a clear visual language, and the design should build on it rather than replace it.

  • Look: isometric, flat-shaded low-poly objects with thin bright edges; deep navy ground with a faint iso grid; lavender faces; aqua and violet status lights. Calm and precise, closer to a product illustration than to neon sci-fi.
  • Why it helps: this style is made of extruded boxes and bevels, so it can be rebuilt procedurally in Three.js at low cost. No Blender pipeline is needed for version one.
  • Existing objects: API Gateway arch, Lambda relay switch, SQS sorter tray, S3 bucket, control-plane tower, GPU cassette, GPU cradle, block-storage volume, pre-warm clock, SSM terminal, two-subnet VPC footprint, mounting cradle.
  • Missing objects: second (GPU) queue, both DLQs, KEDA, Cluster Autoscaler, LiteLLM, LAYA, vLLM, orchestrator and worker pods, idle watchdog, EventBridge stop guard, IAM.
  • Housekeeping: the idle set has 12 renders and the working set 11, the numbering does not line up between sets, and file names mix English and German. Normalise names to component-state.png.

The metaphors in the first draft (portal, processing station, transport system, towers, energetic core, districts) remain valid input. The design phase should still propose three distinct directions, but each must say how it uses or departs from this existing language.

05Modes

Live

Current state of every component: instances, pods, queue depths, GPU busy or idle, provisioning and shutdown in progress, latest event. When everything sleeps, the scene shows it clearly and offers the latest replay.

Replay

Pick a past run and watch its full lifecycle. Timeline with event markers, play/pause, scrub, speed 1× to 60×, captions with timestamps. Long waits (boot, model load) compress automatically and are marked as compressed.

Explore

Orbit, zoom and pan with limits. Click or keyboard-select any object for its role, how it scales, recent activity and metrics. Plain-language and engineer views of the same card.

Guided tour

Added in this revision. A 60–90 second scripted camera path over a real replay, with captions written for non-engineers. This is what most recruiters will see.

  • The two custom in-cluster sources need something running on the control plane. That is a change to the live platform, deployed from this project's own code, and only with the owner's approval.
  • Use source timestamps. Lambda, EC2 and K3s clocks can drift, so replay orders by source time and tolerates a second or two of skew.
  • When the dashboard infers a state, it draws it differently (for example a dashed glow) so the visualisation never claims more than it knows.

07Cost and activity

  • Billed cost from Cost Explorer: monthly and daily by service. It lags about a day, and each API call costs $0.01, so fetch once a day on a schedule and cache. Confirm the account can call Cost Explorer under its organisation.
  • Live estimate: running seconds of each instance × its price (from the Pricing API, matched to On-Demand or Spot), plus persistent EBS. Always labelled "estimate".
  • Activity: jobs per day, outcomes split (completed, rejected by LAYA, needs review, failed), GPU active vs idle time, cold-start duration, average inference duration, estimated cost per job.
  • The headline number for visitors: GPU hours actually paid vs a 24/7 instance for the same period.
  • Present costs inside the scene, for example as a ledger beside the GPU district or a meter on each object, and keep full charts in a drawer.

08Constraints

Public safety

  • Read-only. No endpoint that changes anything.
  • Redact account ID, resource IDs, ARNs, IPs and the wake API URL.
  • No job payloads or outputs; only IDs hashed for display, types and timings.
  • The dashboard's read API has its own minimal IAM role with no access to platform data paths.

Always available

  • The site and its data must not depend on the control plane or GPU being up.
  • Static front end plus a cheap always-on read path.
  • Target under $5/month at rest.

Performance

  • 60 fps desktop, 30+ fps on a mid-range phone.
  • Under 2 MB JS and assets before first interaction; lazy-load the rest.
  • Pause rendering when the tab is hidden.

Accessibility

  • Honour reduced motion with a calmer state-only mode.
  • Every object reachable by keyboard; inspector readable by screen readers.
  • A text event log mirrors what the scene shows.
  • 2D fallback when WebGL is unavailable.
Repository rule

The platform repo (My sleepless slaves) is read-only reference. The dashboard lives entirely in AWS-dashboard, including any AWS resources it needs, which get their own infrastructure code and state.

09Research to do before designing

Kept from the draft, with tighter rules.

  • At least 8 real references across: 3D infrastructure and network visualisation; data-centre and factory digital twins; Three.js and R3F showcase work; isometric miniature worlds; animated data-flow and topology; creative 3D developer portfolios; spatial observability tools; open-source infrastructure visualisers.
  • For each: name, working URL (opened and checked), what is impressive, which pattern transfers, technology where verifiable, and source availability only if the repository was actually found.
  • Describe visuals in words and link to them. Don't copy screenshots into the published brief.
  • Prefer references that match the existing calm isometric style over neon sci-fi.

10Phases

Day 1

Visual prototype

Procedural isometric scene of all components, idle and working states, a typed event model and state machine, replay of a sample trace with timeline and captions, inspector cards. Runs as a static site with no AWS connection. Sample data is labelled as sample.

Week 1–2

Real telemetry

The dashboard's own AWS stack: EventBridge rules, an ingest Lambda, an event table, a read-only API, daily cost fetch. Live mode on AWS-native signals; real runs recorded for replay.

Later

Production polish

In-cluster exporter for pod and job-step events (with approval), guided tour, refined assets, sound design, 2D fallback, performance and accessibility passes.
